# Curating CON's records

How to add to `metadata/` by hand, and what has to be true before it lands.

Most of this tree was machine generated by `con/dump-research-info` and
`zotero`, and that remains the source going forward. What is hand written is
everything the importers do not produce: **temporal extent** (when an
association started and ended), **objectives**, and **evidence for every date**.

```
records/                          the assertions
  .dumpthings.yaml                store config
  XYZProject/   XYZPerson/   XYZOrganization/   XYZPublication/
  XYZAgentRole/ XYZEntityRole/ XYZObjective/    ...
overlays/
  machine-provenance-annotations/ what the importers vouch for (generated)
  curation-evidence/              why we believe a hand-written claim
tools/
  linkml_check.sh                 gate 1: the schema
  validate_records.py             gate 2: the curation rules
```

## Two gates, and neither is redundant

`tools/linkml_check.sh` validates every record against
`demo-research-information` itself — unknown slots, wrong classes, wrong
ranges. `tools/validate_records.py` checks what the schema cannot express:
that a date is backed by evidence, that an evidence pointer still points
where it did, and that a bound faces the right way.

Both had to be made to fail before they could be trusted. The LinkML harness
first reported "No issues found" for four deliberately broken records,
because `linkml-validate --config` was silently validating nothing; it also
exits 0 while printing `[ERROR]`, and an unparseable file surfaced only as a
traceback. The curation gate passed a record violating three of the six rules
it advertised. Both are now fault-injected before use, and a change to either
should be too.

Current state: **343 records, 123 evidenced slots, both gates clean.**

## The encoding, and why it is not ours

Everything below was checked against `things-schemas` and against production
data before being adopted. Earlier drafts of this file invented a parallel
model (`phases`, `actor`, `via`, `status`, `end_kind`, `transitioned_to`,
`supports`); each piece of it turned out to be a worse version of something
that already exists.

### A timed association

`things-prov/v1` gives `Association` — PROV-O's `prov:Association` — two
slots PROV-O does not: `started` and `ended`. So an association *is* the
timed thing:

```yaml
associated_with:
  - schema_type: dlthings:Association     # prov:Association
    object: xyzrins:persons/<slug>        # the agent; Influence.object
    roles: [marcrel:ctb]                  # prov:hadRole, multivalued
    started: {schema_type: dlthings:Start, at_time: "2009-06-15"}
    ended:   {schema_type: dlthings:End,   at_time: "2018-04-06"}
```

Confirmed in production, not only in the schema: the psychoinformatics dump
(`con/visidata-demos`, `psychoinformatics-1/data.jsonl`) holds 5030 records,
43 carrying `associated_with`, 137 associations, **27 of them already using
`started`/`ended` in exactly this form**.

Three consequences:

- **`Association.object` is the agent**, so the person dimension comes free.
  "Hanke opened the Debian package in 2008" is expressible; `actor:
  yoh|con|collaborator:x` was a reinvention of `object` with fewer
  distinctions.
- **`roles` is multivalued**, so concurrent roles need no `phases` list. What
  the old `phases` were really encoding is several associations with the same
  `object` and different spans — which is what `associated_with` is.
- **`Start`/`End` are `EntityInfluence`s** and therefore carry an `object`,
  titled *Trigger*: "End is when an activity is deemed to have been ended by
  an entity, known as trigger". Handing a package to Debian Med is exactly
  that, so `transitioned_to` becomes `ended.object`.

### Two levels of time

`XYZProject` mixes in `ActivityMixin`, so a record has `started`/`ended` of
its own *as well as* per-association ones. They are different claims and
keeping them apart is what lets a record say we were **not** at the
inception:

```yaml
started: {at_time: "2008-04-09"}       # PsychoPy began
associated_with:
  - object: .../yaroslav-halchenko
    started: {at_time: "2009-06-15"}   # we turned up 14 months later
```

`XYZOrganization` mixes in `AgentMixin` instead — an organisation is an
agent, not an activity — so it has no *top-level* `started`. (Nested ones
exist, via `XYZInfluence` and `Delegation`, but they time a *relationship*,
not the organisation's existence.) CON's founding date therefore goes in
`attributes` as `schema:foundingDate`, which is also how that record already
carries its name, short name, prefLabel and description.

That route is a hole in the gate unless the gate knows about it, since
`AttributeSpecification.value` has `range: string` and LinkML will never
check it against `W3CISO8601`. So `dated_slots()` walks
`/attributes/<n>/value` wherever the sibling `predicate` is a known date
predicate, and gives it the span-end it behaves like so the bound rule
applies. The one date in the corpus that was wrong was this one, and it was
wrong precisely because nothing walked it.

### Roles

`roles` has `range: Thing` and is an IRI, never a bare word. The production
dump uses MARC relators and OBO terms, and mints local Things where neither
fits. The minting convention is real but it is *psychoinformatics*':
`pool.psychoinformatics.de-ui/config_default_xyzri.yaml` configures
`xyzri:XYZAgentRole: 'xyzrins:agent-roles/{_randomUUID}'`, and
`psychoinformatics-site-specific` carries five such records.
This repo's own `records/XYZAgentRole/` holds fifteen records, and
mints **none** — every pid there is reused from an external authority
(`marcrel:*`, `obo:*`). Using a readable slug rather than a UUID diverges
from the generator but matches this repo's own `persons/<slug>`,
`projects/<slug>`, `organizations/<slug>` style.

| CON role | IRI | LoC term (their spelling) |
| ------------------ | ----------------------------------- | ------------------------- |
| contributor | `marcrel:ctb` | contributor |
| creator | `marcrel:cre` | creator |
| lead | `marcrel:led` | lead |
| research team member | `marcrel:rtm` | research team member |
| funder | `marcrel:fnd` | funder |
| in-kind host | `marcrel:sht` | supporting host *(see below)* |
| consultant to a project | `marcrel:csp` | consultant to a project |
| Debian maintainer | `xyzrins:agent-roles/debian-maintainer` | — minted here |

`marcrel:fnd` is **funder**, not founder; MARC has no "founder". Easy to get
wrong in exactly the place it matters.

LoC is inconsistent with itself on `sht`: `relacode.html` prints
`spporting host` and `relaterm.html` prints `Supporting host`. The term list
is obviously the right spelling to use; noted only so that nobody "fixes" a
quotation of the code list later.

### Evidence

There is no *dedicated* slot on `Association` for the provenance of a claim.
(`Influence` mixes in `ThingMixin`, so `annotations`, `attributes` and
`characterized_by` are available and the schema says that is deliberate — but
inline annotation would not survive the record/overlay split.) The answer is
not to invent one: this repo already keeps
`metadata/overlays/machine-provenance-annotations/`, whose entries address
the asserted value by **JSON Pointer**:

```yaml
record: xyzrins:projects/datalad
assertions:
  - path: /attributes
    assertion_sha256: sha256:2cd828c3...
    pav:importedBy: xyzrins:source-adapters/dump-research-info/v2
    pav:importedFrom: https://github.com/con/dump-research-info/...
```

`overlays/curation-evidence/` **extends** that shape rather than copying it.
The existing overlays address a *container* (`path: /attributes`, six times
over) and disambiguate by `assertion_sha256`; ours address the exact slot and
drop the hash. That is better at naming and worse at surviving an edit —
the hash was holding the other end — so the validator compares each
assertion's `value` against what the record actually says. Without that,
inserting one association silently re-points every later assertion at a
different claim. With it, the same edit is a hard failure naming both values.

Either way the pointer replaces the old `supports: [start]` tag, which could
only be trusted, never checked.

```yaml
record: xyzrins:projects/psychopy
format: con-association-evidence-v1
assertions:
  - path: /associated_with/0/started/at_time
    value: "2009-06-15"
    bound: upper
    kind: upstream-git        # debian-changelog | upstream-git
                              # | site-git-history | copyright-extract
                              # | publication | registry | recollection
    source: pkg-exppsy:psychopy
    locator: 3e6f7d2dc
    quote: "ensure 2.8 version of wx for IDE"
    note: why this supports the claim, and how far
    confidence: certain       # certain | approximate | unverified
    captured: "2026-10-10"
pending:                      # proposed, NOT asserted in the record
  - proposed_path: /associated_with/-
    proposed_value: {...}
    kind: recollection
    would_confirm: what would settle it
    confidence: unverified
```

PAV's `importedBy`/`importedFrom` describe a machine import; the extra keys
describe a human reading a source and judging what it supports. Both are
overlays on the same record.

## Rules

1. **Every `at_time` is backed.** An evidence `path` must point at it.
   The validator walks the records, not the overlays, so an unbacked date
   fails even if nobody wrote an entry for it.

2. **Bounds point the way the uncertainty does.** An artifact — a repository,
   a changelog, a website's history — never shows the event, only its oldest
   or newest surviving trace.

   | claim | from | real date is | bound | declare |
   | --------- | --------------------- | --------------- | ------- | ------------------ |
   | `started` | the oldest artifact | at or *earlier* | `upper` | (default, `trace`) |
   | `ended` | the newest artifact | at or *later* | `lower` | (default, `trace`) |
   | either | a record of the event | at or *earlier* | `upper` | `artifact: record` |

   The third row used to say `exact`, which contradicted both the validator
   and the corpus: 15 entries derived from a website edit use `upper`, and
   `XYZPublication/datalad-joss-2021.yaml` uses `exact` for a Crossref
   publication date. Both are defensible — a web edit lags the event, a
   registered date does not — but the rule as documented would have rejected
   15 of its own entries. A registry date with no latency is the `exact`
   case, and `registry` is deliberately not in `ARTIFACT_KINDS`, so the
   direction check does not apply to it.

   This is easy to get backwards and we kept doing it. An early draft marked
   a first commit `lower` while marking a whois creation date `upper` — the
   same situation pointing opposite ways. The fix landed in the PsychoPy
   evidence and *not* in the CON evidence, where it survived another round
   because the slot is an attribute and nothing walked it. The harvester's
   `is_lower_bound` field carried the same inversion in its name.

   The cause is that `bound` collides head-on with the colloquial "it's at
   least this old". A field named `direction: at-or-earlier | at-or-later |
   as-stated` would be immune, and is worth considering. Meanwhile the
   validator enforces the direction per slot, and an artifact entry no
   longer gets a free pass because some non-artifact entry sits beside it.

   `bound` is a temporal notion, so it is **rejected** on a non-date slot —
   a role IRI or a trigger IRI. Requiring it there only produced meaningless
   `exact` values.

3. **Recollections are quarantined.** `kind: recollection` requires
   `confidence: unverified` and a `would_confirm`, and lives under `pending`,
   not `assertions` — a record asserts, and we are not asserting this.
   Promoting one means moving it into the record *and* giving it evidence.

4. **The agent is `Association.object`.** Work predating CON is
   `xyzrins:persons/yaroslav-halchenko`, not an institution. The point is not
   to exclude the early work — see below — but to avoid claiming an
   institution signed a 2005 upload.

## The site history is frozen

`whoweare.html` and `projects.html` in con.org are now GENERATED from these
records. So a `site-git-history` citation naming a commit after that point
would be the records quoting themselves — and that is not hypothetical: an
unsourced "Co-Director of the Center for Open Neuroscience" in a person
record acquired a corroborating-looking hit in `hugo-sample/public/`, which
is a page built from that very record.

The freeze is **con.org 53e2e40, 2026-10-08**, titled "Move Jim into
Affiliated Faculty to not overload with 'directorship'" — the last revision
of those pages written by a person. `validate_records.py` enforces it: a
`site-git-history` entry captured after that date must declare
`predates_freeze: true`, and before adding one, check the claim:

    git -C <con.org> merge-base --is-ancestor <locator> 53e2e40

All 36 existing site-history commits were checked this way and all are
ancestors. New facts about who joined when have to come from somewhere other
than the pages the records now write.

## What the gates still cannot see

Both gates check a record against the schema and against its own evidence.
Neither checks a record against the records it *points at*, and two reviews
found the same class of defect through that hole:

- Three DANDI instruments were `generated_by` a project whose `started` was
  thirteen months later. Every date was individually true and the set was
  incoherent.
- A person's association was ended by the first commit filing them under
  Emeritus, without asking whether a later commit moved them back. One did
  (Adina Wagner, con.org 85ca73100), so the store said she had left while her
  own `dlthings:tier` said Collaborator.
- A `pending` entry proposed the wrong agent on the wrong project: its quote
  is YOH about git-annex, and it named Kyle Meyer under scikit-learn. A
  `pending` block is only checked for being quarantined, never for coherence.

A cross-record check is the obvious next gate. Until it exists, these are the
shapes to look for by hand.

## Known pitfalls, learned the hard way

- Dates must be **re-derived from the sources**, not back-inferred from
  whichever quote was handy. The first draft of the PsychoPy record ended the
  contributor phase in 2011 because that was the last quote written down; the
  git log says 2018, and 42 commits — including the whole 2013 CI build-out —
  fell in the gap. It also contradicted this repo's own
  `reports/associations-evidence.json`.
- Site git history is the weakest source here: this repo begins 2011-04-14,
  `projects.html` was renamed from `features.html` on 2015-07-21, and a
  2021-06-16 reorganisation reset most anchors.
- The website's asset for a project is not necessarily its logo. The BIDS
  image on `projects.html` is the before/after directory-tree illustration.
- **Count commits from a clone, with `git shortlog -sne`, and sum every
  spelling.** Two other ways were tried and both lie:

  | method | how it fails |
  | ----------------------------------- | ------------------------------------------------------------------ |
  | `GET /repos/*/contributors` | groups by LINKED ACCOUNT. Jason Gors authors as jason.gors.work@gmail.com, which no account claims, so he is simply absent -- reported here as "no commits under this handle" when there are 61. |
  | `GET /search/commits` grouped by repo | `items` caps at 100 per page, so anyone prolific is undercounted. Kyle Meyer's DataLad commits come back as 77 and are 2318. |

  People commit under several identities and all of them count: Vanessa
  Sochat appears in DataLad as "vsoch", "Vanessa Sochat" and
  "Vanessasaurus", Matteo Visconti di Oleggio Castello as both that and
  "Matteo Visconti dOC" -- 94 PyMVPA commits that a single-spelling count
  reported as 3. Match on surname plus known handles, and add them up.

## When CON itself began

`whois centerforopenneuroscience.org` gives `Creation Date:
2015-07-12T03:00:29Z`, and the first CON content in this repository lands
2015-07-21 — nine days later. The repo's own first commit (2011-04-14, Ben
Nolan) is a buddycloud.com theme import, not CON content.

**CON is a formalisation of work already under way, not a starting gun.** The
pre-2015 efforts — pkg-exppsy (2005), PsychoPy (2009), NeuroDebian (2010),
PyMVPA, DataLad (2013) — are what established the foundation the Center was
built on, and they are the same person's work either way. They belong in
CON's lineage and on the slide. `Association.object` is what lets us say so
precisely: the agent is the person, and CON is simply not mentioned.

## Objectives

Objectives are `XYZObjective` records, linked from the subject by
`influenced_by` with the role `xyzrins:entity-roles/1160471a-9f8e-4379-85f2-351a2a36ef40`
("Long-term goal"). CON's hang off the site-root project, `xyzrins:.`:

```yaml
influenced_by:
- object: xyzrins:objectives/scalable-neural-archiving
  roles:
  - xyzrins:entity-roles/1160471a-9f8e-4379-85f2-351a2a36ef40
  schema_type: xyzri:XYZInfluence
```

Three of the five are **shared with psychoinformatics.de and keep its exact
pids** — self-hosted research IT infrastructure, build tools for
reproducible and shareable science, promote open science through shared data
and collaboration. That is the point of a shared namespace: the same
objective is the same thing, not a near-duplicate with a different id. The
descriptions are copied because each store must hold complete records; if
they ever diverge, that is a curation question, not a modelling one.

Two are CON's own: cross-standards collaboration and harmonization in
neurosciences, and scalable and reliable archiving of neural data.

## Open questions

Narrowed from four; two are now answered.

1. **~~Namespace.~~ Answered: `xyzrins:` is the production namespace.** It
   resolves to `https://concepts.datalad.org/s/demo-research-information/ns/`,
   which reads like a demo — but `psychoinformatics-site-specific`, which
   backs the live psychoinformatics.de, uses it for 1166 of its records, and
   con-site-specific for 317 of 343. It is the shared instance namespace of
   the schema, and sharing it is what lets CON reference psychoinformatics'
   objectives by their own pids rather than minting lookalikes.

2. **~~Record merging.~~ Answered: records must be complete, and the
   question is now moot here.** An earlier draft kept CON's founding date in
   a separate repo as a record carrying only `pid` plus
   `schema:foundingDate`, assuming the store would merge it with the fuller
   record. The code says otherwise:
   `dump_things_service/backends/record_dir_index.py` raises on a duplicate
   IRI; `docs/endpoints.rst` says that when an incoming zone and the curated
   area hold the same PID, "the incoming record is returned" — whole record,
   winner-take-all; and `docs/introduction.rst` puts reconciliation in a
   human curation workflow, explicitly outside the software. There is no
   record-level merge anywhere in the service.

   An incomplete record is not a patch, it is a record that deletes what it
   omits. Since the records now live here, `schema:foundingDate` simply went
   into the one real `XYZOrganization/con.yaml`. `validate_records.py` still
   rejects a duplicate `pid`, because `pid` is the index key and filenames
   are not — two files can collide on pid without colliding on path.

   What remains is **the importers.** Most of this tree is generated: the
   machine overlay records that every `/attributes` slot of `con.yaml` came
   from `con/dump-research-info` via
   `xyzrins:source-adapters/dump-research-info/v2`. A hand-added
   `foundingDate`, the timed associations, and the objectives are all
   candidates for erasure by the next import, and no code links the two, so
   nothing would notice. Does `dump-research-info` need to learn about these,
   or does curation run after import?

3. **Schema version.** The records declare
   `demo-research-information/unreleased`, following `.dumpthings.yaml`. It
   imports `things-prov/v1`, which is `version: 1.0.0` but still
   `status: DRAFT`; meanwhile 19 of the 36 schema directories in the tree
   carry a `DEPRECATED` version, `temporal-mixin` (bare
   `started_at`/`ended_at`) among them.
   Is pinning `unreleased` right, or should these follow a `v1` line?

4. **Is `ended.object` the right home for a handover?** PROV's Trigger is
   "an entity that terminated the activity", which fits Debian Med taking
   over. It is the one piece of our old model mapped onto the schema by
   interpretation rather than by matching an existing use — no `Start`/`End`
   in the production dump carries an `object`.

These are for Michael.
